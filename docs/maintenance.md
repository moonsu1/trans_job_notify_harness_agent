# 수집 감시와 자동 복구 운영

채용 메일은 기존 **3일 간격 13:00**, 유지보수는 **매일 14:00**, 독립 실행 감시는 **30분 간격**입니다. 유지보수는 메일을 보내지 않고 정기 채용 메일에 복구·대기·외부 제한·실행 이상을 요약합니다. Windows에서 로그인 상태를 유지해야 하며 화면 잠금은 가능합니다.

**배치끄기.cmd**는 관련 예약 4개를 모두 비활성화하고 감시 프로그램에도 중지 상태를 기록합니다. 이미 실행 중인 작업은 완료될 수 있으며 수동 실행은 가능합니다. **배치켜기.cmd**는 삭제된 예약도 다시 등록하고, 중지 기간의 밀린 작업을 건너뛴 뒤 기존 3일 간격의 다음 예약부터 실행합니다. **배치상태.cmd**로 상태를 확인합니다. PC를 껐다 켜도 예약 등록과 중지 상태는 유지됩니다.

## 현재 설치 상태

감시·상태 이력·유지보수 그래프·격리 실행기·검증·버전 전환·복원·예약 작업을 구현했습니다. 이 PC에서는 Windows의 가상 머신 플랫폼과 WSL 설치에 필요한 **관리자 확인 단계가 완료되지 않았습니다**. 따라서 Docker에서 생성 수집기를 실행하는 마지막 검증과 자동 코드 복구 활성화는 대기 중입니다. 기존 수집·추천·정기 메일과 무료 상태 점검은 계속 동작합니다.

1. 현재 폴더의 **격리환경설치.cmd**를 실행합니다.
2. Windows 관리자 확인 창에서 허용합니다. WSL2 기능을 켜며 자동 재부팅하지 않습니다.
3. 재부팅 필요 안내가 나오면 작업을 저장하고 직접 재부팅합니다.
4. 다음 로그인 때 `CareerScout-SandboxResume` 작업이 Docker 설치·이미지 빌드·실제 컨테이너 검증을 이어갑니다. 완료되지 않으면 같은 설치 파일을 다시 실행합니다.
5. **설정진단.cmd**에서 `docker_ready: true`, `isolation_setup.stage: ready`를 확인합니다. 이미지 존재만으로 활성화하지 않습니다. 현재 이미지·실행기 지문에 대응하는 실제 검증 기록이 있어야 합니다.

설치 상태는 `%LOCALAPPDATA%\CareerScout\setup\isolation-state.json`, 설치·검증 로그는 같은 `setup` 폴더에 있습니다. Windows 기능을 켜는 관리자 단계는 프로그램이 대신 승인할 수 없습니다.

## 점검과 장애 분류

- 목록 공식 총건수·관측 건수·대상 법인 건수·페이지·관련 JD 확인 건수·채널·버전·응답 구조 지문을 SQLite에 기록합니다. 과거 로그 문자열에서 건수를 추정하지 않습니다.
- 삼성 그룹 공통 목록과 DS 보조 채널을 분리합니다. 공통 목록이 정상이어도 DS 전용 페이지가 차단되면 회사 전체 상태는 부분 수집입니다.
- 최근 정상 관측 5회의 중앙값이 5건 이상이면 70% 이상 감소를 재확인합니다. 양수에서 0건으로 바뀌는 경우는 별도로 확인합니다. 정상 빈 목록은 공식 근거와 재확인으로 판정합니다.
- 다른 회사 게시판, 중복 ID, 페이지 누락, 메뉴·차단 화면을 JD로 읽은 결과를 차단합니다. 근거가 없는 값은 생성하지 않습니다.
- 403·로그인·실제 점검은 외부 제한으로 기록합니다. 같은 구조의 외부 제한을 유료로 반복 진단하지 않습니다. 공고가 없거나 마감됐다고 바꾸지 않습니다.
- 이미지 JD의 원문 대조 대기와 공식 목록 전체 범위 미확인은 계속 부분 수집입니다. 수집기 코드를 바꿨다는 이유로 정상으로 올리지 않습니다.

**수집상태점검.cmd**는 API·메일 없이 실제 사이트를 점검하고 `reports/latest-health.html`을 엽니다. 원본 응답과 상세 JSON은 `%LOCALAPPDATA%\CareerScout\maintenance`에 저장합니다.

## 코드 복구와 적용 제한

`maintain`은 기존 수집 경로를 먼저 재확인하고, 구조 오류를 재현한 경우에만 현재 모델에 수집기 수정안을 요청합니다. 정상 점검은 모델을 호출하지 않습니다. 하루 최대 2개 장애, 장애당 최대 2개 수정안입니다. 단순 건수 감소만으로 코드를 바꾸지 않습니다.

모델에는 관련 수집기 소스와 필요한 공개 응답만 전달합니다. 후보자 이력·API 키·메일 인증 정보는 제외합니다. 모델은 URL·필드·선택자를 읽는 `collect(api, company)` 모듈만 만들 수 있습니다. 설정·선호·평가·예산·메일·검증기를 바꾸는 권한은 없습니다.

생성 코드는 검증과 운영 모두 Docker 안에서 실행합니다. 직접 네트워크·운영 DB·자격 증명·사용자 폴더·Docker 소켓을 제공하지 않습니다. 호스트가 허용한 읽기 전용 공개 수집 Tool만 쓸 수 있습니다. 컨테이너는 비관리자, 읽기 전용 파일 시스템, CPU·메모리·프로세스·시간 제한을 사용합니다. Docker가 없을 때 호스트에서 실행하는 대체 경로는 없습니다.

출력은 원문을 가리키는 참조입니다. 보호된 호스트 검증기가 원래 응답에서 값을 다시 추출해 법인·공고 ID·URL·본문·건수·페이지를 대조합니다. 공식 사이트에서 연결된 새 채용 URL만 실제 기업과 게시판 범위를 검증한 뒤 허용합니다. 검색 결과만으로 도메인 권한을 넓히지 않습니다.

자동 적용에는 과거 정상 원문의 고정 사례, 기존 회귀 테스트, **30초 이상 간격을 둔 두 번의 신규 실사이트 확인**, 적용 직전 코드·설정 지문 확인이 필요합니다. 긍정 공고 자료가 없거나 JD·법인·페이지를 확인하지 못하면 적용을 보류합니다. 현재 자동 승격은 검증 자료를 갖춘 주 목록 수집기에 연결되어 있습니다. 독립 검증 자료를 확보하지 못한 보조 채널은 복구 대기로 유지합니다.

회사별 버전 파일을 보관하고 SQLite 트랜잭션으로 활성 포인터만 바꿉니다. 적용 후 첫 3회를 포함해 이후 모든 실행에서 원문 검증을 반복합니다. 타기업 혼입·허위 필드·새 버전만의 파싱 오류·파일 변조는 이전 버전으로 복원하고 잘못된 버전을 격리합니다. 외부 네트워크 장애는 코드 회귀로 단정하지 않습니다.

전체 API 예산은 **$0.90/일·$10/월**, 그 안의 복구 예산은 **$0.10/일·$1/월**입니다. 추가 결제 한도가 아닙니다. 예약 시점에 한도를 확인하고 정산하며, 부족하면 무료 점검만 계속합니다. 유료 웹 검색은 복구 단계에 사용하지 않습니다.

## 실행 감시와 중단 처리

`career_scout/watchdog.py`는 Python 표준 라이브러리만 사용합니다. 본 프로그램의 import 오류도 시작 기록과 종료 코드로 확인합니다. 예정 슬롯·단계별 heartbeat·프로세스 생성 시각과 실행 파일을 확인하고, 누락·중단 작업은 최신 예정 작업 한 번만 보충하며 재시도는 한 번으로 제한합니다.

주 배치가 유지보수보다 우선합니다. 중단된 해당 작업의 컨테이너만 정리합니다. 메일 실패는 저장된 발송 대기열만 재시도하고 분석을 반복하지 않습니다. `sent`, `sending`, `uncertain`은 자동 재전송하지 않습니다. PC가 꺼져 있거나 인터넷이 없는 동안 외부 알림을 보낼 수 없으며 복귀 후 누락을 확인합니다.

새 정기 메일에는 이전에 보낸 공고도 포함해 현재 추천·검토 후보 전체를 반복해서 표시합니다. 위 전송 상태 제한은 동일 메일의 불확실한 SMTP 재시도에 적용되며, 다음 예약일에 생성하는 전체 후보 리포트는 별개입니다. 메일 주기는 기존 3일 간격 13:00입니다.

## 명령어

현재 폴더의 PowerShell에서 실행합니다.

```powershell
.venv\Scripts\python.exe -m career_scout.cli doctor
.venv\Scripts\python.exe -m career_scout.cli health --no-api
.venv\Scripts\python.exe -m career_scout.cli maintain
.venv\Scripts\python.exe -m career_scout.cli incidents
.venv\Scripts\python.exe -m career_scout.cli repair 장애ID --dry-run
.venv\Scripts\python.exe -m career_scout.cli rollback 회사ID
.venv\Scripts\python.exe -m career_scout.watchdog tick --dry-run
```

`repair --dry-run`은 수정안 생성·검증까지 하며 적용하지 않습니다. API 호출에는 같은 예산을 적용합니다. `health`는 API를 사용하지 않습니다. `maintain --no-api`도 무료 점검만 수행합니다.
